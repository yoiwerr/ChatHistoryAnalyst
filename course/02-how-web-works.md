## 第一层：你的请求怎么到达服务器

### TCP/IP 协议栈 —— 寄快递的类比

你在淘宝下了一个单（HTTP 请求），商品是一段 HTML 代码。这个包裹的旅行分四层：

| 层 | 类比 | 实际协议 | 你请求里的内容 |
|----|------|----------|---------------|
| 应用层 | 你写的信 | HTTP | `GET / HTTP/1.1` |
| 传输层 | 快递单号（顺丰/TNT） | TCP | 源端口 54321 → 目标端口 80 |
| 网络层 | 收件地址 | IP | 源 IP 你的电脑 → 目标 IP 服务器公网 IP |
| 链路层 | 快递卡车走哪条路 | 以太网/WiFi | MAC 地址，路由跳转 |

**整个过程大致是：**

```
你的电脑生成一个 HTTP 请求 GET / HTTP/1.1
↓
TCP 把它包上一层：目标端口 80（HTTP 默认端口）
↓
IP 再包一层：目标地址 42.193.x.x（你的服务器公网 IP）
↓
数据包在互联网上经过 N 个路由器，最终抵达阿里云的数据中心
↓
服务器的网卡收到这个包
```

一个更直观的快递类比：

- **IP 地址** = 收件地址（"浙江省杭州市余杭区 xxx"）——定位到哪台机器
- **端口号** = 收件人姓名（"张三"）——定位到机器上的哪个程序
- **TCP** = 顺丰快递——保证不丢件、顺序不乱、送到了会确认

`42.193.x.x:80` 这个地址的意思就是：**找到 42.193.x.x 这台机器上的 80 号端口程序**。

## 第二层：数据包到了服务器之后

服务器网卡收到数据包后，Linux 内核开始拆包：

```
网卡接收数据
↓
内核网络栈：检查 IP 头，确认是发给本机的（目标 IP = 本机公网 IP）
↓
检查 TCP 头：目标端口 = 80
↓
内核查找"谁在监听 80 端口？"
↓
发现：Docker 的 docker-proxy 进程绑定了 0.0.0.0:80
↓
把数据包交给 docker-proxy
```

### 等等——"谁在监听端口 80"是什么意思？

每个服务器程序想接收网络数据，都得向操作系统"注册"：

```bash
# 用这个命令能看到谁注册了哪个端口
ss -tlnp | grep :80

# 输出：
# LISTEN 0 511  0.0.0.0:80  0.0.0.0:*  users:(("docker-proxy",pid=1234,fd=6))
```

这行输出说的是：
- `LISTEN`：我在监听
- `0.0.0.0:80`：只要是发给我 80 端口的数据我都收（`0.0.0.0` 意思是"不挑来源 IP"）
- `docker-proxy`：是 Docker 的代理进程在收

## 第三层：Docker 网桥 —— 数据包怎么进入容器

这是 Docker 最精妙的设计之一——**虚拟网络**。

### 宿主机视图（真实的物理网络）

```
服务器物理网卡 eth0
IP: 172.19.122.126 (内网 IP)
公网 IP: 42.193.x.x (通过 NAT 映射)
```

### Docker 虚拟网络视图（容器看到的网络）

```
                    宿主机
               ┌─────────────┐
               │   iptables   │  ← 做 NAT（网络地址转换）
               │   端口映射   │
               └──────┬──────┘
                      │
               ┌──────▼──────┐
               │  docker0     │  ← Docker 创建的虚拟交换机
               │  172.17.0.1  │
               └──┬───┬───┬──┘
                  │   │   │
    ┌─────────────┘   │   └─────────────┐
    ▼                 ▼                  ▼
┌────────┐    ┌────────────┐    ┌────────────┐
│ nginx  │    │ streamlit  │    │   api      │
│.0.4:80 │    │ .0.3:8501  │    │ .0.2:8000  │
└────────┘    └────────────┘    └────────────┘
```

关键概念：**docker0 是一个虚拟网桥**，相当于 Docker 在宿主机内部建了一个"局域网"。

- 宿主机自己在这个局域网里的地址是 `172.17.0.1`
- 每个容器被分配一个 `172.17.0.x` 的 IP
- 容器之间可以通过这个内部 IP 直接通信
- **容器之间不需要通过宿主机端口**！Nginx 容器访问 API 容器时，直接走 `api:8000`（Docker 内部 DNS 会解析成 `172.17.0.2:8000`）

### 端口映射的原理

再看 `docker-compose.yml`：

```yaml
nginx:
    ports:
      - "80:80"    # 这行非常关键
```

这行 `"80:80"` 的意思是：
- **左边 80**：宿主机的 80 端口（对外暴露）
- **右边 80**：容器内部的 80 端口（容器内 Nginx 监听的端口）
- 效果：发往宿主机 80 端口的数据，自动转发到容器内的 80 端口

**为什么 Streamlit 的 8501 和 API 的 8000 没有 `ports`？** 因为它们不需要对外暴露。外部请求经过 Nginx 转发就够了。端口暴露得越少，越安全。

```
外部用户 → 宿主机:80 → Docker端口映射 → nginx容器:80 → 内部路由 → streamlit:8501 或 api:8000
```

## 第四层：Nginx 容器收到请求后的路由

Nginx 是"反向代理"（reverse proxy）——它自己不产生内容，只是一个**收发员**。

看 `nginx/nginx.conf` 的配置逻辑：

```
请求 URI                         Nginx 的决策
─────────────────────────────────────────────────
GET /                            → 转发给 streamlit:8501（前端页面）
GET /_stcore/stream              → 转发给 streamlit:8501（WebSocket 连接）
GET /api/v1/imported_files       → 转发给 api:8000（后端 API）
GET /api/docs                    → 转发给 api:8000（Swagger 文档）
```

判断逻辑在 Nginx 配置中用 `location` 块实现：

```nginx
location / {                    # 匹配一切以 / 开头的请求
    proxy_pass http://streamlit:8501;   # → 转给前端
}

location /api {                 # 匹配 /api 开头的请求（优先级更高）
    proxy_pass http://api:8000;         # → 转给后端
}
```

注意：`streamlit` 和 `api` 这里不是真实的域名或 IP，而是 Docker 的内部 DNS 名称！Docker 会把它解析成对应容器的内部 IP（`172.17.0.2`、`172.17.0.3`）。

## 第五层：应用处理并返回

最后一步，Streamlit 或 FastAPI 处理请求，生成 HTML/JSON 响应，原路返回。

**以访问首页为例，完整路径：**

```
1. 你在浏览器输入 http://42.193.x.x
2. 你的电脑生成 HTTP 请求：GET /
3. TCP 包上目标端口 80，IP 包上目标地址 42.193.x.x
4. 经过互联网 N 跳，到达阿里云服务器网卡
5. Linux 内核看到目标端口 80，交给 docker-proxy
6. docker-proxy 转发到 Docker 网桥 docker0
7. docker0 根据端口映射，发到 Nginx 容器的 80 端口
8. Nginx 看到请求路径是 /，匹配 location /，转发到 streamlit:8501
9. Streamlit 生成 HTML 页面，返回
10. 响应数据包原路回到你的浏览器
11. 浏览器渲染 HTML，你看到了 ChatLab 粉色主题界面
```

全程大概 11 步，但对你来说只需要输入一个地址按回车。这就是 Docker 和 Nginx 帮你吞掉的复杂度。
